# FaceVitals Development Workflow

This document describes the workflows supported by the Python files currently supplied in `FaceVitals_Python_Codes.zip`.

## 1. Two ways to run FaceVitals

FaceVitals currently has two distinct execution paths:

- **Offline research pipeline:** processes a recorded camera session through CSV files. This path supports POS, CHROM, heart-rate estimation, signal-quality analysis, stability analysis and comparisons.
- **Live application:** `facevitals_app.py` runs camera capture, face detection, RGB extraction, POS processing, filtering and heart-rate estimation in one Tkinter application.

The offline scripts are useful for algorithm development and analysis. The live application is the integrated real-time demonstration.

## 2. Offline POS workflow

The `run_facevitals.py` launcher runs this exact sequence:

1. `rgb_extraction.py` — captures webcam frames, detects a face using MediaPipe Face Landmarker, extracts RGB averages from forehead and cheek regions, and writes `rgb_signals.csv`.
2. `resample_rgb.py` — checks timestamps and gaps, selects the longest continuous valid segment, resamples RGB measurements to 30 Hz, and writes `rgb_signals_resampled.csv`.
3. `plot_rgb_signals.py` — plots the original RGB traces from `rgb_signals.csv` for visual inspection. It does not create a new CSV.
4. `pos_algoritm.py` — reads `rgb_signals_resampled.csv`, computes POS signals for the three facial regions, and writes `pos_signals.csv` plus `pos_signals_complete.png`.
5. `filtering.py` — reads `pos_signals.csv`, applies a fourth-order Butterworth band-pass filter (0.7–3.5 Hz in this implementation) to the valid continuous signal segment, and writes `filtered_signals.csv` and `filtered_signals.png`.
6. `heart_rate.py` — reads `filtered_signals.csv`, estimates rolling regional and combined heart rate, and writes `heart_rate_results.csv` and `heart_rate_spectrum.png`.
7. `signal_quality.py` — reads `filtered_signals.csv`, calculates signal-quality metrics, and writes `signal_quality_results.csv` and `signal_quality_scores.png`.

Run from the project directory:

```powershell
python run_facevitals.py
```

The launcher invokes each script sequentially using the same Python interpreter and stops if a stage returns an error. The RGB capture stage requires a working webcam and the MediaPipe model file `face_landmarker.task`.

## 3. Offline CHROM workflow

The CHROM path is separate; `run_facevitals.py` does **not** launch it.

1. Run `rgb_extraction.py` to create `rgb_signals.csv`.
2. Run `resample_rgb.py` to create `rgb_signals_resampled.csv`.
3. Run `chrom_algorithm.py`. It reads the resampled RGB file, computes CHROM signals, and writes `chrom_signals.csv` and a plot.
4. Run `chrom_filtering.py`. It reads `chrom_signals.csv` and writes `chrom_filtered_signals.csv` and a plot. Inspect its code before interpreting this as a second independent band-pass stage: the CHROM algorithm already applies filtering to its X and Y components within its processing windows.
5. Run `chrom_heart_rate.py`. It reads `chrom_filtered_signals.csv` and writes `chrom_heart_rate_results.csv` and a spectrum plot.
6. Run `chrom_signal_quality.py`. It reads `chrom_filtered_signals.csv` and writes `chrom_signal_quality_results.csv` and `chrom_signal_quality_scores.png`.

Run these scripts individually in the order above from the project directory.

## 4. Analysis and comparison scripts

These scripts operate on files generated by the processing paths; they are not required to launch the live application.

| Script | Required input | Main output / purpose |
|---|---|---|
| `pos_stability_analysis.py` | `heart_rate_results.csv` | Regional and combined POS HR stability summary (`pos_stability_summary.csv`) |
| `chrom_stability_analysis.py` | `chrom_heart_rate_results.csv` | CHROM HR stability summary |
| `compare_pos_chrom.py` | POS and CHROM HR results plus both quality result CSVs | Combined comparison CSV and HR/quality comparison plots |
| `comapre_pos_chrom.py` | POS and CHROM HR result CSVs | Earlier/narrower HR-only comparison; filename contains a spelling error |
| `chrom_signal_quality.py` | `chrom_filtered_signals.csv` | CHROM signal-quality assessment |
| `signal_quality.py` | `filtered_signals.csv` | POS signal-quality assessment |

For the full comparison, `compare_pos_chrom.py` expects all four result files:
- `heart_rate_results.csv`
- `chrom_heart_rate_results.csv`
- `signal_quality_results.csv`
- `chrom_signal_quality_results.csv`

## 5. Live application workflow

Run:

```powershell
python facevitals_app.py
```

The app integrates:
- OpenCV camera capture;
- MediaPipe Face Landmarker face detection;
- three facial RGB regions;
- live POS window processing and overlap-add;
- causal filtering for live signals;
- rolling heart-rate and spectral-confidence estimation;
- Tkinter display and CSV recording.

The app requires `face_landmarker.task` in the project directory. Use the app's Start/Stop controls and save the recording CSV through its interface.

`face_detection.py` and `roi_extraction.py` are standalone visual development utilities. They demonstrate face landmarks and ROI placement; they are not called by `facevitals_app.py`.

## 6. Utility and diagnostic scripts

- `webcam.py` and `camera_test.py`: simple webcam access checks.
- `check_timestamps.py`: inspects timestamp continuity in `rgb_signals.csv`.
- `check_segments.py`: identifies continuous recording segments and gaps in `rgb_signals.csv`.
- `check_columns.py`: prints/checks the columns in `pos_signals.csv`.
- `plot_rgb_signals.py`: visualizes the RGB channels in `rgb_signals.csv`.

These are supporting tools, not mandatory stages of the main live app.

## 7. Important implementation notes

1. **The launcher is POS-only.** The `run_facevitals.py` pipeline does not execute CHROM, stability analysis or POS-vs-CHROM comparison.
2. **Different HR bands appear in the quality scripts.** `heart_rate.py` and `chrom_heart_rate.py` use 0.7–3.5 Hz, while `signal_quality.py` and `chrom_signal_quality.py` define 0.7–3.0 Hz. Keep this difference visible in reports and decide with the team whether to harmonize it.
3. **Offline and live filtering differ.** The offline POS script uses zero-phase filtering; the live application uses causal filtering because future samples are not available in real time.
4. **CHROM filtering deserves review.** `chrom_algorithm.py` filters the CHROM X/Y components within short processing windows. `chrom_filtering.py` is a later stage in the saved-file workflow. Review both implementations together before describing them as two separate equivalent band-pass filters.
5. **The current ROI/skin approach is experimental.** The offline RGB extractor uses rectangular facial regions and HSV skin masking. This should not be presented as proven robust across all skin tones, lighting conditions or occlusions.
6. **A stable-looking heart-rate trace is not proof of accuracy.** Clinical or competition performance must be assessed against synchronized independent reference measurements.
